# Aura demo website

The Aura phone app running in a browser, so people can try it from a link. You get a clickable 390×844 phone
with short story sections around it. Each visitor sees the same demo person, read live from the **dev** backend
(us-west-1), and anything a visitor changes stays in their own browser.

## How the data flows

```
browser ──GET /snapshot──▶ CloudFront (d1u96rboj5xs6k.cloudfront.net, 60 s cache, only /snapshot and /health)
                              │ OAC (signed)
                              ▼
                           Function URL (AWS_IAM) ──▶ Lambda aura-dev-demo-site
                                                         │ signs in as the demo user (secret aura/dev/demo-site)
                                                         ▼
                                                      the normal service APIs (GET only)
```

- **The site never writes to AWS.** Visitor edits go into an overlay in `localStorage`
  (`aura-demo:local`), drawn over the shared snapshot (`src/lib/local.ts`). The chip above the phone shows a
  **Reset** button.
- The last good snapshot is kept in `localStorage` (`aura-demo:snapshot`), so a reload draws at once. If AWS
  can't be reached, the site uses the bundled `src/data/sample.json`.
- No password, token or email ever reaches the browser. The backend is the `aura-dev-demo-site` stack in
  `../../aws_docs/services/demo-site`.

## Run it

```sh
npm install
npm run dev        # http://localhost:5173
npm test           # vitest
npm run build      # typecheck + static files in dist/
npm run preview    # serve dist/
```

The API address comes from `VITE_DEMO_API` in `.env.local`. It's a public URL, not a secret (see
`.env.example`). Leave it unset and the site runs on the bundled sample.

`dist/` is plain files, so any static host can serve it. GitHub Pages builds and publishes it on every push to
the `demo-website` branch (`.github/workflows/pages.yml`).

## Tools (run from `tools/` with uv)

```sh
uv run python create_account.py     # once: makes the shared demo user and fills the secret (prints the email only)
uv run python seed.py               # profile, consent, the month of band data that raises the alerts
uv run python seed.py --extras      # after NI-04 fired: next 14 days of calendar + today's water
uv run python seed.py --calendar    # top the calendar up later
QT_QPA_PLATFORM=offscreen uv run python export_catalog.py   # refresh src/data/catalog.json
```

To refresh the bundled sample after seeding, save a fresh snapshot over it:
`curl -s https://d1u96rboj5xs6k.cloudfront.net/snapshot -o ../src/data/sample.json`

The demo account lives in the dev Cognito pool. Its sign-in is kept only in Secrets Manager (`aura/dev/demo-site`)
and Windows Credential Manager, never in this repo.

## Left out on purpose

These are in the app but don't belong in a public demo: sign-in and sign-out, the Test lab, data export, and
deleting the account. Feature codes (DX-01…) appear only in the story list, never inside the phone.

On the calendar you can drag a block to a new time (15-minute steps), stretch it by its bottom edge, drop it on a
day in the grid, or drag a to-do into the hours. Hold at the hours' side edge to flip the day, or on ‹ › to flip
the week. Touch needs a short hold first, so a swipe still scrolls.

The bedtime reminder and wake alarm ring (a toast and a short tone) only while the page is open, like the PC app.
A session running on another device would show in Sessions, but the demo account never has one.

Recovery lists one alert per feature (its newest). The app lists every open day, but the demo's month was sent all
at once, which would leave about 95 rows.

## The calendar coach (Auto-allocate)

The full calendar (`src/calendar/CalendarCard.tsx`, `ZonesPage.tsx`) shades each work day with a recovery rhythm
read from a **capacity score** and the person's work and lunch hours (`src/calendar/dayZones.ts`): light and heavy
work, short and heavy (lunch) recovery. **Auto-allocate** (the button shows while there are open to-dos) plans the
day around that rhythm (`src/calendar/allocate.ts`, shown in `AllocateSheet.tsx`):

- **Recovery zones are fixed rest.** No task is placed on one. A to-do **too big** for any single free gap is split
  into pieces that fit around the recovery zones and before its deadline. An **already-committed** work/focus block
  that crosses a recovery zone is **split in place** around it (its hidden source is tagged `auto:'split-src'`, its
  pieces shown as amber `auto:'part'` work sessions). A **meeting** on a recovery zone is left alone with a warning —
  a meeting can't be moved.
- **Tough work goes first, and earns a break.** After each heavy task (`demand ≥ DEEP_DEMAND` 67) the coach slots a
  short recovery break and projects a capacity gain. Tapping that break on the day raises the capacity score
  (`RECOVERY_RESTORE`), so a re-run fits a little more in.
- Each run is **idempotent**: prior `auto:'part'`/recovery events are cleared and recomputed from scratch.

**Adding a task asks what the coach needs** (`src/calendar/ItemSheet.tsx`, written by `src/calendar/rows.ts`):

- **Duration** → `estimateMinutes` (how long to reserve).
- **Toughness** — Light / Focused / Hard / Deep → `demand` 25 / 55 / 72 / 88 (Deep ≥ 67 earns a recovery break).
- **Deadline** — a day, optionally with a "finish before" time. Stored as `deadlineAt` / `deadlineHasTime`, kept
  **apart** from `dueAt`/`hasTime` (a scheduled time), so an untimed to-do can carry a hard deadline and still be
  auto-allocated. A time is a hard cap; a day-only deadline just orders the queue (`deadlineOf` in `allocate.ts`).

All of this is a browser-only overlay — nothing is written back to AWS.

## Today, Recovery and Logging

- **Home → Today** shows only what is due today (`todayItems` in `src/calendar/homeParts.ts`), in this order:
  - today's open alerts;
  - recovery events still ahead today, with Start;
  - the mood and connection check-ins not done yet;
  - the sleep check, when it's due;
  - water until the goal;
  - strength while the last 7 days have fewer than 2 strength days.

  Items drop off once done. The seeded alerts are dated 19 Oct or earlier, so in the demo Today rarely shows an
  alert; Recovery has them all.
- **Recovery** (`src/screens/Recovery.tsx`) has three parts, top to bottom.
  - **Often used:** the 4 things used most, features and modes mixed. Scores come from
    `src/recovery/usage.ts`: the 30-day uses the visitor noted (`LocalState.used`) plus the sessions, logs,
    check-ins and planned events already in the data. With no history, it shows up to 2 open-alert features and
    then default modes.
  - **The 16 recovery features in six groups:**
    - The busiest group comes first, and mode uses count towards their group.
    - Each row shows its status and its one-verb action, which works even with no open alert.
    - The feature's log sits under the row (`src/recovery/logCards.tsx`).
    - BS-01 and BS-02 stay on Home.
  - **Modes:** 4 tiles, never repeating Often used, and **Show more**. Show more opens the Modes page inside
    Recovery (`src/recovery/ModesPage.tsx`), which has shelf chips and a set-up page per mode.
- **Modes** (`src/lib/modes.ts`) holds 65 modes in 10 shelves: Focus, Breathe, Meditate, Sleep, Rest, Movement,
  Mind, Outside, People and Fuel.
  - They come from the Swift app (`origin/main` c022c0d): the 50 recovery presets, the focus modes, the breathing
    patterns and the guided meditations.
  - The old presets and modes resolve through aliases.
  - `startMode` (`src/lib/actions.ts`) runs each kind:
    - a timer, or a flow (open-ended) run;
    - a breathing pacer with In / Hold / Out;
    - guided prompts;
    - the wind-down;
    - a calendar plan, for Day off and Alcohol-free evening.
  - Search no longer lists Modes, but typing a mode's name finds it.
  - The list moves to the PyQt `core/features.py` in the port.
- **Search → Logging** holds everything else the app logs, from the Zoho tab "Categories and Sources": 105 rows in
  13 categories (`src/logbook/kinds.ts`).
  - Typed-in items get a form (`forms.tsx`, including the 1-minute Quick check).
  - Computed items are worked out from logs, the calendar and sessions (`derive.ts`).
  - Items only the band or the desktop app can measure say so, with no number.
  - Every entry is saved as a local `logs` row.

## Keeping it fresh

A month's alerts age out of the lookback after a few weeks. To refresh, make a new demo user (`create_account.py`),
which updates the secret, then seed again. Deleting the old user is an AWS write, so ask first.
